01Core concepts

Image vs container

An image is a read-only snapshot (like a class or an installer). A container is a running instance of it (like an object). One image can start many containers.

Container vs VM

VMContainer
Own OS kernelYesNo, shares host kernel
SizeGBsMBs
StartupMinutesSeconds or less
IsolationStronger (hardware level)Process level (namespaces + cgroups)
How isolation works

Namespaces control what a process can see (own PIDs, network, filesystem, hostname). cgroups control how much it can use (CPU, memory).

Layers and the build cache

Every RUN, COPY, ADD creates a layer, and layers are cached. When a layer changes, every layer after it rebuilds. So order from least to most frequently changing.

Step 1: two filesystems. Where does COPY copy from and to?

This is the part that confuses everyone. There are two separate places, and every Dockerfile line works in one or the other:

  • The source is always relative to the build context: the folder you pass at the end of docker build ... . (the . means "this folder"). Docker packs that folder (minus anything in .dockerignore) and sends it to the Docker engine.
  • The destination is a path inside the image's Linux filesystem. A relative destination (./, .) is relative to the current WORKDIR.
  • Which OS? Your files live on your OS (Windows/Mac/Linux). The image is always Linux. On Windows and Mac, Docker Desktop runs a small Linux VM (WSL2) and the build happens there. That's why paths inside the Dockerfile use Linux style (/app, forward slashes, case-sensitive) even on Windows.
  • RUN runs inside the image (a temporary Linux container), not on your computer. RUN npm install executes with the Linux files you already copied in, which is why you must COPY package.json before it.

Step 4: why the bad order is bad (and in what sense it's "wrong")

Honest wording

The bad order is not broken. It builds a working image. It is wrong for performance: every tiny code change throws away the cached npm install and downloads all dependencies again, which wastes minutes per build, bandwidth and CI money.

The rule Docker uses:

  • Docker builds layers top to bottom and reuses a cached layer only if the instruction is identical and every layer above it was reused.
  • For COPY, "identical" means the content of the copied files is unchanged (it checksums them).
  • For RUN, "identical" means the command text is unchanged and the layer before it was reused. Docker does not look at what the command would do.

Instructions people mix up

Six pairs that look similar but behave differently. For each: what each one means, why it matters, and exactly how it behaves with an example. First, one picture that explains half of them.

The big picture: build time vs run time

1. CMD vs ENTRYPOINT

CMD

What: the default command (or default arguments) of the container.

Key property: anything you type after the image name in docker run replaces it completely.

ENTRYPOINT

What: the fixed program the container always runs.

Key property: whatever you type after the image name is appended as arguments to it. Only --entrypoint replaces it.

Why it matters: it decides whether someone can easily run a different command in your image (debugging with a shell) or whether the image behaves like a single fixed tool.

Example A: CMD only (what you use for most web apps)

Example B: ENTRYPOINT + CMD (the program is fixed, the argument has a default)

The rule, as a formula: the final command = ENTRYPOINT + (CMD or whatever you typed after the image name).

Real-world use of ENTRYPOINT: a tool image. ENTRYPOINT ["curl"] lets users run docker run mycurl -I https://example.com, so the image is the tool. Official images like Postgres use an ENTRYPOINT script that does setup and then starts the server with the CMD.

Rule of thumb

A normal app (API, website): use CMD only, so you can always docker run -it myapp sh to debug. A tool or an image with a setup script: use ENTRYPOINT, and put default arguments in CMD.

2. COPY vs ADD

COPY

Copies files/folders from your build context into the image. Only that. Nothing hidden.

ADD

Does everything COPY does, plus two extras: it auto-extracts local .tar/.tar.gz files, and it can download a URL.

Why it matters: "extra features" mean surprises. With ADD, you can't tell by reading the line whether a file stays a file or explodes into a folder.

The URL feature is also a trap: ADD https://example.com/tool.zip /tmp/ downloads at build time with no integrity check by default, isn't reproducible (the URL's content can change), and doesn't extract zip files. Prefer an explicit RUN curl -fsSL ... && sha256sum -c ... so you can verify it.

Rule of thumb

Always write COPY. Use ADD only on purpose, when you specifically want a local tar archive unpacked into the image.

3. RUN vs CMD

RUN

Executes while the image is being built. Its result (files created or changed) is saved into the image as a layer. Runs once.

CMD

Does nothing during the build. It's a note saying "when a container starts, run this". Runs every time you start a container.

Why it matters (the mistake to avoid): putting install work in CMD.

RUNCMD
When it executesdocker builddocker run / docker start

How many allowedAs many as you likeOnly the last one counts
Typical contentnpm install, apk add curl, npm run build["node","server.js"]
Rule of thumb

Preparing the image (install, compile, create folders) → RUN. Starting the app → CMD/ENTRYPOINT.

4. ARG vs ENV

ARG

A variable that exists only while building. Set with docker build --build-arg NAME=value. The running container does not have it.

ENV

A variable stored in the image. Available to later build steps and to the running container. Can be overridden at docker run -e.

Why it matters: picking the wrong one means either your app can't see the value at runtime (ARG), or you've hard-wired a value you wanted to choose per build.

ARGENV
Available during buildYes (after it's declared)Yes (after it's set)
Available in the running containerNoYes

Neither is for secrets

ARG values appear in docker history and ENV values in docker inspect. Pass real secrets at runtime (secrets manager, --env-file) or use BuildKit secret mounts.

5. EXPOSE vs -p

EXPOSE 3000

A note stored in the image: "the app inside listens on 3000". It opens nothing and changes no networking.

-p 8080:3000

A docker run option that publishes the port: host port 8080 forwards to container port 3000.

Why it matters: the most common "my container runs but I can't open it in the browser" cause is a missing -p.

Two details interviewers like

1) Other containers on the same Docker network can reach container:3000 with or without EXPOSE or -p. Publishing is only for traffic coming from outside (your browser, the host).
2) The order is always HOST:CONTAINER. -p 3000:8080 is the reverse of -p 8080:3000.

6. Shell form vs exec form

Shell form

CMD node server.js

Docker runs it as /bin/sh -c "node server.js". A shell becomes the main process (PID 1), and node is its child.

Exec form

CMD ["node","server.js"]

Docker runs node directly. Your app is PID 1. No shell involved.

Why it matters: docker stop sends a termination signal (SIGTERM) to PID 1. If PID 1 is a shell, your app may never receive it.

Rule of thumb

Use exec form for CMD and ENTRYPOINT so signals reach your app. Shell form is fine for RUN (you often want && and pipes there). If you need shell features at start, use a script that ends with exec node server.js.

One-sentence answers to say in an interview

CMD vs ENTRYPOINT: ENTRYPOINT is the fixed program, CMD is replaceable default arguments. COPY vs ADD: COPY just copies; ADD also unpacks tarballs and fetches URLs, so I use COPY. RUN vs CMD: RUN runs at build time and is saved in the image, CMD runs every time the container starts. ARG vs ENV: ARG exists only during build, ENV also exists in the running container. EXPOSE vs -p: EXPOSE is documentation, -p actually publishes a port. Shell vs exec form: exec form makes my app PID 1 so it receives SIGTERM.

Networking

  • Default bridge: containers reach each other by IP only.
  • User-defined bridge (what Compose creates): containers reach each other by service name via built-in DNS, e.g. http://api:3000.
  • localhost inside a container means that container itself. Not your machine, not another container.
  • -p 8080:3000 means host 8080 → container 3000.
  • Other drivers: host (shares host network, Linux), none, overlay (multi-host).

Container lifecycle and stopping

What actually happens when a container starts?

A container is not a virtual machine and not a thread. docker run asks the Linux kernel to start one ordinary process, wrapped in restrictions. That process is the container's PID 1.

The five things the kernel does for a new container (in order):

  1. Create namespaces. New isolated "views": its own process IDs, network stack, mounts, hostname.
  2. Build the root filesystem. The image layers are stacked (read-only) with a writable layer on top, and that becomes / for the process.
  3. Apply cgroups. Memory/CPU/process-count limits (-m 256m, --cpus 0.5).
  4. Drop privileges. Remove most root powers (capabilities) and filter dangerous system calls (seccomp).
  5. exec your command. ENTRYPOINT/CMD (e.g. node server.js) replaces the setup code, and it is now PID 1.

Why it's "PID 1", and what that means

  • A container lives exactly as long as PID 1. When PID 1 of a PID namespace exits, the kernel kills everything else in it, and Docker marks the container Exited.
  • docker run alpine echo hi → PID 1 is echo, finishes in a millisecond → container exits at once. That's the classic "my container exits immediately".
  • A web server stays up because node server.js never finishes: it keeps listening.
  • Process or thread? A process. It may spawn more processes or threads inside (Node worker threads, nginx workers, JVM threads). They all live in that namespace.
PID 1 is special

1) Signals: the kernel gives PID 1 no default signal behavior. With no SIGTERM handler in your code, docker stop does nothing and Docker kills it after 10 s (exit 137). That's why Node apps need process.on('SIGTERM', …).
2) Zombies: PID 1 must reap orphaned child processes. Most apps don't, so docker run --init (or init: true) puts a tiny init (tini) in front.

Prove it yourself:

How many containers can you create?

Docker has no fixed maximum. You can start containers until some resource on the host runs out. The limiting resource depends on what the containers do, and it's usually memory.

Linux fundamentals behind Docker

Docker is mostly a friendly wrapper around Linux kernel features. Learn these ideas once and Docker (and Kubernetes) stop being magic.

1. Processes, PIDs, parent and child

  • Every running program is a process with a PID. A process starts another with fork (copy itself) then exec (turn into a different program). That's how the shell starts node.
  • Processes form a tree: each has a parent. On a normal Linux machine PID 1 is init/systemd. In a container, PID 1 is your app.
  • If a parent dies, children become orphans and get adopted by PID 1. A finished child nobody has "collected" is a zombie, and PID 1 must collect it.
  • Info about every process lives in /proc/<pid>/. /proc/1/cmdline is PID 1's command.

2. Kernel, user space and system calls

  • The kernel controls hardware, memory and processes. Programs run in user space and ask the kernel for things through system calls (open a file, send a packet, start a process).
  • All containers on a host share one kernel. That's why they're light, and why a Linux container needs a Linux kernel (Docker Desktop on Windows/Mac runs a Linux VM for that).
  • A container's "OS" (Alpine, Ubuntu…) is just a set of files and libraries, not a kernel.

3. Namespaces: what a process can see

That is, in a nutshell, what docker run does, plus a root filesystem and cgroup limits.

4. cgroups: how much a process can use

  • Control groups put processes in a group and cap its resources: memory, CPU, number of processes, disk I/O.
  • docker run -m 256m --cpus 0.5 --pids-limit 100 myapp writes those numbers into the container's cgroup.
  • Memory over the limit → the kernel's OOM killer kills a process (container exit 137, OOMKilled: true). CPU over the limit → throttled, not killed.
  • Files live under /sys/fs/cgroup/ (cgroup v2: memory.max, cpu.max).

5. Filesystem: how a container gets its files

In one sentence

A container's files are a stack of read-only layers from the image, plus one thin writable layer on top. Linux shows that stack as one normal folder tree (/). The technology that does the stacking is called overlayfs.

The problem it solves. Every container needs its own complete set of files (/bin, /etc, /app…), and 20 containers from the same image shouldn't need 20 full copies on disk, or take seconds to copy at start. Overlayfs lets them share the image files and only store what each container changes.

Analogy: a stack of transparent slides

Picture overhead-projector slides. The bottom slide has the base drawing (the operating system). On top you lay a slide with your node_modules, then a slide with your code. Looking down from above you see one combined picture. If two slides draw the same thing, the higher slide wins. The container gets one extra blank slide on top that it is allowed to draw on. All the slides below are glued down and never change.

What is a "mount"? (plain English)

  • A mount means "attach some storage at this folder path". Linux builds its single / tree out of many mounts: your disk at /, a USB stick at /mnt/usb, and so on.
  • A container gets its own private list of mounts (that's the mount namespace). Docker puts these in it:
    • / → the overlayfs stack described above
    • /proc, /sys, /dev → kernel information and devices
    • your volumes and bind mounts → at the paths you chose
  • The container's / is not your host's /. The kernel swaps the root for the process (the idea behind chroot/pivot_root), so the process cannot even see host files outside its tree.

Everything is a file

In Linux, almost everything is presented as a file: normal files, folders, devices (/dev/null), running-process info (/proc), kernel settings (/sys), even network sockets. That's why one set of tools (cat, ls, echo) can inspect so much, and why Docker can hand a container a private view of "files" for almost everything.

6. Signals and exit codes

Exit codes: 0 = success, 1 = generic error, 128 + N = killed by signal N. So 137 = 128+9 (SIGKILL / OOM) and 143 = 128+15 (SIGTERM).

7. stdin / stdout / stderr and file descriptors

  • Every process starts with three open file descriptors: 0 stdin, 1 stdout, 2 stderr.
  • docker logs just reads the container's stdout/stderr. That is why apps should log to stdout instead of files.
  • Sockets, files and pipes all use file descriptors, which is why "too many open files" is a real limit under load.

8. Users, permissions and capabilities

  • Every process runs as a UID (0 = root). Files have an owner and permission bits (rwx for user/group/others). permission denied usually means a UID/ownership mismatch (Bug #25).
  • Root in a container is still real root on the host unless user namespaces are used, but with fewer powers. That's why you run as non-root (USER node).
  • Capabilities split "root powers" into pieces (e.g. NET_BIND_SERVICE = bind ports below 1024). Docker drops most by default; cap_drop: [ALL] is the strict setup.

9. Networking plumbing

  • Each container gets its own network namespace with its own localhost. That's why localhost never reaches another container (Bug #1).
  • Docker connects it to the host with a veth pair (a virtual cable) plugged into a bridge (a virtual switch, docker0 or a custom network).
  • Outbound traffic is NATed through the host. -p 8080:3000 adds an iptables DNAT rule: traffic to host port 8080 is rewritten to the container's IP:3000.
  • Inspect: ip addr, ip route, ss -tlnp (listening ports), iptables -t nat -L.

10. /proc and /sys: the kernel as files

  • /proc exposes processes and kernel state: /proc/<pid>/status, /proc/meminfo, /proc/sys/kernel/pid_max.
  • /sys exposes devices and cgroups. Tools like ps, top, free just read these files.
  • A pitfall: inside a container, old tools may read host-wide numbers from /proc (total RAM) instead of the container's limit. That's why JVMs and Node needed container-aware settings.

11. Init systems vs containers

A normal server boots systemd as PID 1, which starts many services. A container doesn't boot an OS: PID 1 is your single app. That's why "one process per container" is the standard design, and why you don't ssh into containers or use systemctl inside them. Use docker exec instead.

Your 5-line mental model

1) A container = one Linux process started by runc. 2) Namespaces limit what it sees, cgroups limit what it uses. 3) Its / is the image layers stacked with overlayfs plus a writable layer. 4) It's PID 1: when it exits, the container is done, and it must handle SIGTERM. 5) All containers share the host kernel, so they're light but less isolated than VMs.

Say it in an interview

"A container is just a Linux process, isolated with namespaces and limited with cgroups, running on a root filesystem built from image layers with overlayfs. It's PID 1 in its own PID namespace, so it lives exactly as long as that process, and it shares the host kernel, which is why it starts in milliseconds and why it's lighter but less isolated than a VM."

02Production practices

1. Multi-stage builds (the thing to mention first)

Short version: build in a big image, ship from a small one. The rest of this section explains the problem it fixes, how it works, and walks through a complete project file by file.

The problem: a single-stage image ships your whole workshop

To build an app you need heavy tools: compilers, a package manager, devDependencies, source code. To run it you need almost none of that. With a normal one-stage Dockerfile, everything used to build ends up inside the final image.

Need at build timeNeed at run time
Compiler (tsc, javac, Go toolchain)The compiled output (dist/, app.jar, a binary)
Build tools (Maven, npm, webpack/Vite)The runtime (Node, a JRE, or nothing for a static binary)
devDependencies, test librariesProduction dependencies only
Source codeConfig and the files the app reads

The idea: two (or more) images in one Dockerfile

You write several FROM blocks (stages). Early stages are your workshop: build everything there. The last stage is a clean small image, and you COPY --from= only the finished result into it. Docker keeps only the last stage as the image you ship; the earlier stages are discarded (they only live in the build cache).

How it works, step by step

  1. Each FROM starts a brand-new, empty filesystem. Stage 2 can't see stage 1's files unless you copy them.
  2. AS name labels a stage so you can refer to it later (AS build).
  3. COPY --from=build /app/dist ./dist copies files from another stage's filesystem (not from your computer) into the current stage. This is the only bridge between stages.
  4. The final image = the last stage. Everything not copied across (compilers, devDependencies, source, caches) is simply not in it.
  5. Build cache still works per stage, so rebuilds stay fast. BuildKit even builds independent stages in parallel and skips stages the final image doesn't use.
Link to what you learned earlier

Plain COPY src dest reads from your build context (your computer). COPY --from=stage src dest reads from another stage's filesystem inside the build. Same instruction, different source.

A complete example project (Node + TypeScript API)

TypeScript is the perfect example: browsers and Node can't run .ts files, so you must compile first. The compiler is needed to build and useless afterwards.

Each file, and why it matters for the build:

  • dependencies = needed at runtime (express). devDependencies = needed only to build (typescript, type definitions). This split is exactly what multi-stage exploits.
  • "build": "tsc" compiles src/*.ts into dist/*.js. "start" runs the compiled file.
  • rootDir: src → read TypeScript from src/. outDir: dist → write JavaScript to dist/. That dist/ folder is "the artifact" we ship.
  • .dockerignore keeps your host node_modules and dist out of the build context, so stages build everything fresh inside Linux.

Before: the single-stage Dockerfile

It works, but the final image contains: the full Debian-based node:20 image, TypeScript and all devDependencies, the src/ TypeScript, and npm's cache. You ship ~1 GB to run ~20 lines of JavaScript.

Production examples you'll meet

A. React/Vite frontend → nginx. The final image has no Node at all, just nginx and static files.

  • Build stage ≈ 1 GB with Node and thousands of packages. Final image ≈ 50 MB. Node never runs in production here; nginx just serves files.

B. Spring Boot (Maven) → JRE. You need the JDK + Maven to compile, but only a JRE to run the jar.

  • maven:… is ~700 MB (JDK + Maven + ~/.m2 download cache). eclipse-temurin:21-jre is far smaller, with no compiler or Maven.
  • COPY --from=build /workspace/target/*.jar app.jar: copies the built jar from stage 1 and renames it app.jar. (The wildcard must match exactly one jar.) See Lab 2 for the layered-jar version.

C. Go → almost nothing. Go compiles to one static binary, so the runtime image can be nearly empty.

  • ~800 MB build image → a final image around 10–20 MB with no shell, no package manager. That's why compiled languages love multi-stage.

D. Next.js: deps → builder → runner with output: 'standalone'. See Lab 3 for the complete file.

Say it in an interview

"Before multi-stage, my production images carried the compiler, devDependencies and source because I built and ran in the same image. With multi-stage I build in one stage with all the tooling, then copy only the compiled output and production dependencies into a small runtime stage, running as a non-root user with a healthcheck. Typically that cuts a Node image from about 1 GB to under 200 MB, and removes the compiler and source from production, which means faster deploys and a smaller attack surface."

2. Small, specific base image

  • node:20-alpine: small, but uses musl libc. If native modules (bcrypt, sharp) break, use -slim.
  • eclipse-temurin:21-jre for Java runtime (JRE, not JDK).
  • distroless: no shell, tiny attack surface.
  • Pin versions: node:20.11-alpine, not node:latest.

3. Non-root and .dockerignore

If an attacker breaks out of your app, root in the container is dangerous. Use USER node (shipped in node images) or create a user. And always add a .dockerignore: smaller context, no leaked secrets, and the host's node_modules can't overwrite the container's.

4. Config and secrets

Never

COPY .env or ENV DB_PASSWORD=... in a Dockerfile. It stays in image layers forever (docker history shows it).

Do

Inject at runtime: --env-file, Compose environment:, or secret managers (Docker/K8s Secrets, AWS Secrets Manager, Vault). One image for every environment (12-factor).

Build-time secrets (private npm token): RUN --mount=type=secret,id=npmrc ... (BuildKit). It doesn't persist in layers.

5. Healthchecks

"Running" ≠ "ready". A DB container is running seconds before it accepts connections.

Gotcha

Use 127.0.0.1, not localhost. On Alpine, localhost can resolve to IPv6 ::1 while your app listens on IPv4 only, so the check fails and the container is marked unhealthy (see Bug #33).

6. Logging, limits, restarts

  • Log to stdout/stderr, not files. Docker collects them; log drivers ship them to ELK/Loki/CloudWatch.
  • No limits → one leaky container can eat the host. Java: -XX:MaxRAMPercentage=75. Node: --max-old-space-size below the limit.
  • A crash loop means read the logs. The restart policy only hides it.

7. Security checklist

  • Non-root user
  • Minimal base image, pinned tag or digest
  • No secrets in layers
  • Scan images in CI: trivy image myimage or docker scout cves myimage
  • Read-only root filesystem (read_only: true) where possible
  • Drop capabilities (cap_drop: [ALL])
  • Never mount /var/run/docker.sock into containers (it's root on the host)
  • Resource limits set

8. Build speed

  • Order layers by change frequency.
  • BuildKit cache mounts: RUN --mount=type=cache,target=/root/.npm npm ci
  • CI: --cache-from / --cache-to (registry or GitHub Actions cache).
  • Multi-platform: docker buildx build --platform linux/amd64,linux/arm64. Built on an M1 Mac and the amd64 server says exec format error? That's why.

10. Docker vs Kubernetes

Docker/Compose builds and runs containers on one host. Kubernetes orchestrates many containers across many hosts: scaling, self-healing, rolling updates, service discovery, secrets. Compose is great for dev and small deployments; K8s when you need scale and high availability.

03Monolith vs microservices

Monolith + Docker

One image, one deployable. docker compose up gives you the whole system. Scale = run more replicas behind a load balancer. Dockerizing a monolith is the easiest first step and makes a later split easier.

Microservices + Docker

  1. One service = one image = one process. Don't cram two services into one container.
  2. Database per service. No shared tables, or it's a distributed monolith.
  3. Talk by service name over a shared network (http://users:3000). Never localhost, never hard-coded IPs.
  4. Only the gateway is published. Internal services have no ports:, so they're unreachable from outside.
  5. Each service has its own healthcheck and env config.
  6. Version independently: users:1.4.0, orders:2.1.3.
  7. Startup order isn't guaranteed. Use healthchecks plus retry logic in code. depends_on only helps locally.
  8. Use async messaging (RabbitMQ/Kafka) for things that shouldn't fail together.
  9. Observability: stdout logs plus a request/correlation ID passed between services.

depends_on vs ready

Network isolation pattern

Put gateway + services on frontend, services + DBs on backend. A service on both networks bridges them, and the DB sits only on backend, so the gateway can't reach it.

Does Docker work well with Next.js? Yes.

  • Set output: 'standalone' in next.config.js. Next copies only what's needed → image ~150 MB instead of 1 GB+.
  • NEXT_PUBLIC_* variables are inlined at build time. Setting them at docker run is too late. Pass them as build ARGs or load config at runtime. Great interview point.
  • Bind to all interfaces: HOSTNAME=0.0.0.0.
  • Two different API URLs: the browser uses the public URL, server-side code uses the internal Docker name.

Does Docker work well with Spring Boot? Yes.

  • Multi-stage: Maven/Gradle in a JDK stage → run the JAR on a JRE stage.
  • Layered jars (-Djarmode=layertools): dependency layers get cached; only your code layer changes. Or skip the Dockerfile: ./mvnw spring-boot:build-image.
  • Actuator /actuator/health for the HEALTHCHECK.
  • Config via env: SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/app (relaxed binding).
  • Slow startup → generous healthcheck start_period (~40 s) so it isn't killed while booting.

Lab 1: Node + Postgres + Redis (production style)

Run it:

Prove you understand it. Do each and explain what happened:

  1. docker compose down then up -d → hit /visits. DB rows persisted (volume). Redis counter reset (no volume).
  2. docker compose down -v → data gone. -v deletes volumes.
  3. docker compose logs -f api while you stop db → watch the behaviour.
  4. docker compose stop api → fast = SIGTERM handled. Compare after changing to shell-form CMD.
  5. docker exec -it <api> sh → whoami should be node, not root.
  6. docker images then docker history <image> → see size and layers.
  7. Break it: set DB_HOST=localhost → read the error → fix (Bug #1).
  8. Cache experiment: edit server.js and rebuild → npm step says CACHED. Edit package.json → it reruns.

07Last-minute cheatsheet

Say first

Image = recipe, container = running instance. Shares kernel; namespaces + cgroups.

Dockerfile

Order for cache · multi-stage · slim base · non-root · exec-form CMD · .dockerignore.

Networking

Service names, not localhost. Publish only the gateway. 0.0.0.0, not 127.0.0.1.

Data

Named volumes for DBs. Volume ≠ backup. Init scripts run once.

Startup

Healthcheck + service_healthy + app-level retry.

Config

Env at runtime. Never secrets in layers. NEXT_PUBLIC_* is build-time.

Exit codes

0 normal · 1 app error · 137 SIGKILL/OOM · 143 SIGTERM.

Debug

ps -a → logs → inspect → exec → compose config → minimal repro.
