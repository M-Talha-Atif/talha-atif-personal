Kubernetes Interview Prep

Understand what Kubernetes actually does, deploy real apps with it, and debug the failures interviewers love to ask about. Assumes you already know Docker.

Your one-minute pitch (memorize)

"Kubernetes is a container orchestrator. I tell it the desired state, like 'run 3 copies of this image, expose them on port 80', and its controllers keep reality matching that, restarting crashed pods, replacing dead nodes and rolling out new versions without downtime. I deploy with Deployments and Services, configure with ConfigMaps and Secrets, protect apps with readiness and liveness probes plus resource requests and limits, and run stateful things like databases with StatefulSets and PersistentVolumes. When something breaks I go get → describe → logs --previous → exec, because the events usually name the cause."

01Core concepts

What problem does Kubernetes solve?

Docker runs a container on one machine. In production you need many containers over many machines: what restarts a crashed one, spreads load, rolls out v2 safely, or moves work when a server dies? That's orchestration. Kubernetes (K8s) is the standard answer.

The key idea: declarative desired state

You don't say "start 3 containers". You say "I want 3 replicas of this image" and Kubernetes keeps making it true. Kill a pod and it creates another. That's why it's called self-healing.

Cluster architecture

The reconciliation loop

Pod: the smallest unit

A Pod wraps one or more containers that share a network namespace (one IP, localhost between them) and can share volumes. Usually 1 app container. Extra containers are sidecars (log shipper, proxy) or init containers (run to completion first, e.g. wait for DB or run migrations).

Pods are disposable

A pod's IP and name change every time it's recreated. Never depend on a pod IP. Never run bare Pods in production; use a controller (Deployment etc.) that recreates them.

Deployment → ReplicaSet → Pods

Labels and selectors: how objects find each other

Almost everything connects through labels (key/value tags like app=web) and selectors (queries on those tags). A Deployment selects its pods; a Service selects the pods to send traffic to. A selector typo = a Service with no endpoints (the classic bug).

Service: a stable address for changing pods

Ingress: one entry point, many services

Config and Secrets

Secrets are not secret by default

They're only base64-encoded in etcd. Anyone who can read the Secret (RBAC) or etcd can decode them. Enable encryption at rest, lock down RBAC, and prefer an external manager (Vault, AWS Secrets Manager via External Secrets).

Probes and pod lifecycle

Gotcha

Don't make liveness depend on the database or another service. If the DB hiccups, every pod gets restarted at once and you turn a blip into an outage. Keep liveness cheap and local; put dependencies in readiness.

02Production best practices

  1. Set resource requests and limits on every container. Without requests the scheduler is blind and HPA can't work. Without a memory limit one leak hurts the whole node.
  2. Add readiness and liveness (and startup for slow apps) probes. Readiness is what makes rolling updates zero-downtime.
  3. Never use :latest. Pin a version or digest, tag images with the git SHA. imagePullPolicy defaults to Always for :latest.
  4. Run replicas ≥ 2 for anything user-facing, with topologySpreadConstraints or pod anti-affinity so replicas don't share a node or zone.
  5. Use a PodDisruptionBudget (minAvailable: 1) so node drains and upgrades can't evict all replicas at once.
  6. Autoscale: HPA for pods, Cluster Autoscaler/Karpenter for nodes. HPA needs requests and metrics-server.
  7. Handle shutdown gracefully: handle SIGTERM, add a short preStop sleep, set terminationGracePeriodSeconds above your longest request.
  8. Use namespaces + ResourceQuota/LimitRange to separate teams and environments and cap blast radius.
  9. RBAC with least privilege. One ServiceAccount per app, no cluster-admin for workloads, disable token automount if the pod doesn't call the API.
  10. Harden pods: runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation: false, capabilities.drop: [ALL], Pod Security Standards (restricted).
  11. NetworkPolicies: default deny, then allow only the flows you need (and DNS egress).
  12. Keep config out of images: ConfigMaps/Secrets, one image for every environment; per-env differences via Kustomize overlays or Helm values.
  13. Ship via GitOps (Argo CD / Flux): Git is the source of truth, rollbacks are git revert.
  14. Observe: logs to stdout (collected by Fluent Bit/Loki), metrics (Prometheus + Grafana), alerts on restarts, Pending pods and error rates.

Zero-downtime shutdown: the race to know

Security checklist

  • Non-root, read-only root filesystem, no privilege escalation, capabilities dropped
  • Pinned image tags/digests; images scanned in CI (Trivy/Grype); signed if possible
  • Secrets encrypted at rest or from an external manager; not committed to Git
  • RBAC least privilege; no wildcard roles; audit logging on
  • NetworkPolicies default-deny
  • Namespaces with ResourceQuota/LimitRange
  • API server not exposed publicly; admin access via SSO/IAM, short-lived credentials
  • Regular upgrades (control plane + nodes); etcd backups tested

03Real-world scenarios

From Docker Compose to Kubernetes

You already know Compose, so map it. This is a strong answer to "how would you migrate?".

Tooling

kompose convert can bootstrap manifests from a Compose file. Treat the output as a draft, since you'll still add probes, resources and security settings.

Monolith on Kubernetes

One Deployment (with a readiness probe), one Service, an Ingress, config in a ConfigMap/Secret, and a managed database outside the cluster (RDS/Cloud SQL) or a StatefulSet. You gain rolling updates, restart-on-failure, and horizontal scaling for free, even without splitting the app.

Microservices on Kubernetes

  • One Deployment + Service per microservice, versioned and rolled out independently.
  • Service discovery is built in (cluster DNS). Cross-namespace: users.shop.svc.cluster.local.
  • Service mesh (Istio, Linkerd) adds mTLS, retries, traffic splitting, and tracing without code changes. Mention it as "when you need it", not by default.
  • Resilience still lives in your code or mesh: timeouts, retries with backoff, circuit breakers. Kubernetes doesn't add those.

Deployment strategies

StrategyHowTrade-off
Rolling (default)Replace pods gradually (maxSurge, maxUnavailable)Simple, no extra capacity; both versions live briefly, so be backward-compatible
RecreateKill all, then start newDowntime; use when versions can't coexist
Blue/greenRun a full second copy, flip the Service selector or IngressInstant rollback; double the resources
CanarySend 5% to the new version, then increaseSafest; needs traffic splitting (Argo Rollouts, ingress annotations, mesh)

Autoscaling: three layers

  • HPA (Horizontal Pod Autoscaler): more/fewer pods based on CPU, memory or custom metrics. Formula: desired = ceil(current × currentMetric / target). Needs metrics-server and CPU requests.
  • VPA: adjusts a pod's requests/limits (don't combine with HPA on the same metric).
  • Cluster Autoscaler / Karpenter: adds nodes when pods are Pending for lack of resources, and removes idle ones.

Config per environment: Helm vs Kustomize

Kustomize: base YAML + overlays (dev, prod) that patch replicas, images, resources. No templating, built into kubectl -k. Helm: templated packages (charts) with values.yaml, versioned releases and rollbacks; great for installing third-party software (ingress-nginx, Prometheus). Common combo: Helm for third-party, Kustomize for your own apps.

GitOps delivery

Managed vs self-managed

EKS, GKE and AKS run the control plane for you (upgrades, etcd, HA). You manage nodes (or use serverless/auto modes), networking add-ons and workloads. Self-managing (kubeadm, k3s) is for on-prem or learning. In most interviews: "managed unless there's a reason not to".

Lab 1: Deployment + Service (self-healing, scaling, rollouts)

  1. Self-healing: kubectl delete pod <one-web-pod> → a new one appears within seconds (ReplicaSet controller). Note the new name and IP.
  2. Scale: kubectl scale deploy/web --replicas=5, then check get endpoints web. Scale back to 3.
  3. Rolling update: kubectl set image deploy/web nginx=nginx:1.27-alpine and watch kubectl get pods -w. Note old and new pods overlapping (maxSurge). Then kubectl get rs: two ReplicaSets.
  4. Break it: kubectl set image deploy/web nginx=nginx:1.99-doesnotexist → new pod goes ImagePullBackOff, but the old pods keep serving (maxUnavailable 0). kubectl rollout status deploy/web hangs. Diagnose with describe pod, then recover with kubectl rollout undo deploy/web.
  5. History: kubectl rollout history deploy/web.
  6. Selector mismatch: kubectl edit svc web, change the selector to app: wbe → get endpoints web is empty, curl fails. Explain why, then fix it (Bug #13).
  7. Declarative proof: edit replicas: 2 in the file and kubectl apply -f app.yaml. Compare with kubectl scale and say why Git should hold the truth.

Lab 2: ConfigMap, Secret, probes, resources, security context

The app is a tiny dependency-free Node server. Its code travels in a ConfigMap (generated by Kustomize), so there is no image to build.

  1. Probes in action: watch get pods during the first 8 s. Pods are Running but not Ready. Run kubectl get endpoints api during that window: empty.
  2. Readiness vs liveness: curl localhost:8080/unready on one pod → it drops out of get endpoints api, RESTARTS stays 0. Then curl localhost:8080/crash → the container exits and RESTARTS increases. Explain the difference.
  3. Config injection: the JSON shows greeting and apiKeyConfigured: true. Decode the secret: kubectl get secret -o jsonpath='{.items[0].data.API_KEY}' | base64 -d. Say why base64 is not encryption.
  4. ConfigMap change → rollout: edit the literal in kustomization.yaml, kubectl apply -k ., and watch a rolling update start by itself. The hash-suffixed name changed, so the Deployment spec changed.
  5. Resources: lower the memory limit to 16Mi, apply → describe pod shows OOMKilled / exit 137 (Bug #6). Put it back.
  6. Security context: kubectl exec deploy/api -- id shows uid 1000. Try kubectl exec deploy/api -- touch /x → fails (read-only root FS).
  7. Break it: change configMapKeyRef.key to NOPE → pod goes CreateContainerConfigError (Bug #4). Read the event, fix it.

Lab 3: Microservices (users + orders), DNS, HPA, NetworkPolicy

The same two services as the Docker Lab 4, now with Deployments and Services. orders calls http://users:3000, resolved by cluster DNS.

On disk these are separate files (hpa.yaml, networkpolicy.yaml, namespace.yaml) plus users/server.js and orders/server.js (identical to the Docker Lab 4 services) and an optional ingress.yaml.

  1. Service DNS: kubectl run -n shop dns --rm -it --image=busybox:1.36 -- nslookup users → resolves to the ClusterIP. Then try nslookup users.shop.svc.cluster.local from the default namespace and plain users from default (fails, so explain why: Bug #16).
  2. Resilience: kubectl scale -n shop deploy/users --replicas=0 → curl /orders/1 returns the 502 JSON from the app, and get endpoints users is empty. Scale back up and it recovers with no restart of orders.
  3. Load balancing: scale users to 3 and watch get endpoints -n shop users list 3 IPs.
  4. HPA: kubectl get hpa -n shop. If it shows <unknown> you don't have metrics-server (Bug #27). Install it, then generate load: kubectl run -n shop load --rm -it --image=busybox:1.36 -- sh -c "while true; do wget -qO- http://orders:3000/orders/1 >/dev/null; done" and watch replicas grow.
  5. NetworkPolicy (only on a CNI that enforces it, e.g. Calico/Cilium): from a temporary pod without the app=orders label, wget -qO- -T2 http://users:3000/health should time out.
  6. Ingress (optional): install ingress-nginx, apply ingress.yaml, then curl -H "Host: shop.localhost" http://localhost/orders/1. Explain the role of the controller vs the Ingress object.
  7. Rolling update on a code change: edit users/server.js (e.g. add a user), kubectl apply -k . → the ConfigMap hash changes → users pods roll automatically.

Lab 4: StatefulSet Postgres with persistent storage

  1. Persistence: run the commands above. The pod was destroyed but the data survived because the same PVC (data-pg-0) re-attached to the new pg-0.
  2. Stable identity: kubectl run -it --rm c --image=busybox:1.36 -- nslookup pg-0.pg. Explain headless Service + StatefulSet DNS.
  3. PVC outlives the StatefulSet: kubectl delete sts pg then kubectl get pvc → still there. Re-apply and the data returns. Say why that is a safety feature (and when you must delete PVCs manually).
  4. Break it: remove the PGDATA env var on a cluster whose volume has lost+found → initdb error (Bug #23).
  5. Discuss: why many teams use a managed DB (RDS/Cloud SQL) or an operator (CloudNativePG, Zalando) instead of a hand-written StatefulSet: backups, failover, upgrades.

07Last-minute cheatsheet

Mental model

Declare desired state; controllers reconcile forever. Pods are disposable.

Objects

Deployment → ReplicaSet → Pod. Service finds pods by label. Ingress routes HTTP to Services.

Workloads

Deployment stateless · StatefulSet identity + disk · DaemonSet per node · Job/CronJob batch.

Probes

Startup holds off the rest · readiness = traffic · liveness = restart. Liveness never checks dependencies.

Resources

Requests = scheduling + HPA. Limits = ceiling. CPU throttles, memory OOMKills (137).

Config

ConfigMap/Secret via env or volume. Env needs a restart. Secrets are base64, not encryption.

Rollouts

maxSurge/maxUnavailable + readiness. rollout status/undo. preStop sleep for zero-downtime.

Debug

get → describe (Events) → logs --previous → exec → get endpoints → events -A → node.
